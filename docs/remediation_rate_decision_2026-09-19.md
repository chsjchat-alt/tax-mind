## 一、两种口径的对照

### V4 §3.2 评分定义卡（目标口径）

> **整改率（Remediation Rate）= 已验证整改项权重 ÷ 可整改项权重**
> （「已验证」以整改证据经人工确认并回溯留痕为准）
> 调整后分 = 原始分 × (1 − 整改率)

要点：① 是一个**比值**（∈ [0,1]）；② 分子要求**人工验证 + 证据留痕**；③ 分子分母均带**权重**。

### 当前代码实现（`backend/app/core/compliance_adjustment.py`）

```python
reduction_pct = min(0.80, completion_count × 0.15)
# completion_count = remediation_tasks 中 status=COMPLETED 且 source="compliance" 的任务数
# 0.15 / 0.80 来自 risk_config（reduction_pct_per_task / reduction_pct_max，B1 已配置化）
```

要点：① **线性累加**（非比值），每完成 1 个合规任务固定降 15%；② **无验证环节**——用户点「完成」（status=COMPLETED）即计入；③ **等权**——每个任务权重相同；④ 需 80% 封顶防超过 100%。

## 二、歧义点清单（7 项）

| # | 歧义点 | V4 要求 | 当前实现 | 差距 |
|---|--------|---------|----------|------|
| A1 | **「已验证」如何认定** | 整改证据经**人工确认**并回溯留痕 | `status=COMPLETED` 即计入，模型无 `verified_by`/`verified_at`/证据字段 | 缺整个人工复核环节（审核报告 #8） |
| A2 | **分母「可整改项」指什么** | 可整改项（权重和） | 无分母概念（线性累加） | 候选定义见 Q1，差异极大 |
| A3 | **「权重」取自哪里** | 分子分母均按权重计 | 每任务等权 15% | 模型已有 `priority`(high/medium/low) 与 `compliance_tags` 可作权重来源，但未启用 |
| A4 | **80% 上限是否保留** | 比值口径天然 ≤100%，无需封顶 | 线性口径必须封顶（R ≤ D 约束） | 切换到比值后 cap 去留需决策 |
| A5 | **部分整改如何处理** | 评分口径需明确「部分整改的处理」 | 二元状态（COMPLETED 与否）；`progress` 字段存在但不参与计算 | 部分完成是否计部分权重未定义 |
| A6 | **分母为 0 的兜底** | 未定义 | 无任务 → reduction=0，靠 `is_fully_compliant` 分支强制 10 分 | 比值口径下 0/0 需显式定义 |
| A7 | **manual 任务是否纳入** | 未明确 | 只统计 `source="compliance"`（合规校验自动生成） | 手动任务算不算「可整改项」影响分母 |

## 三、可选方案

### 方案 A：维持线性口径 + 补验证环节（改动最小）

- 保留「任务数 × 15%，cap 80%」公式不变；
- 仅新增验证门槛：模型加 `verified_by`/`verified_at`，完成接口拆为「标记完成 → 人工确认」两步，算分时只统计已验证任务。

| 维度 | 影响 |
|------|------|
| 与 V4 字面符合度 | ❌ 仍为线性累加，非「权重比」 |
| 代码改动 | 小：模型 2 字段 + 迁移 + 1 处查询过滤 + 确认接口 |
| 分数行为 | 未验证任务不再降分 → 调整后分短期升高（更保守） |
| 历史数据 | 存量 COMPLETED 任务需追溯标记（建议默认「已验证」以免分数跳变） |
| 前端 | 任务列表加「待确认/已确认」状态 |

### 方案 B：严格 V4 权重比口径（最贴合方案）

- 整改率 = Σ(已验证任务权重) ÷ Σ(可整改任务权重)；
- 权重 = priority 映射（high=3 / medium=2 / low=1）；
- 分母 = 全部 `source="compliance"` 任务（含未完成）——「可整改项」操作化为「合规校验生成的整改项」；
- 保留验证环节（同方案 A）；80% cap 废除（比值天然 ≤100%，全部验证完成 → 调整后分 = 0，或产品决定是否设最低分）。

| 维度 | 影响 |
|------|------|
| 与 V4 字面符合度 | ✅ 完全符合定义卡 |
| 代码改动 | 大：模型迁移（verified 字段）+ 引擎分子分母改造 + 权重映射 + 前端「整改率」展示改为百分比 + 相关测试（test_compliance_adjustment 等约 10 处断言）全部改写 |
| 分数行为 | **显著变化**：当前 3 任务即降 45%；比值口径下 3/3 全部验证才降 100%、3/6 只降 50%——降幅普遍变小，调整后分普遍升高 |
| 历史数据 | 需迁移脚本：存量 COMPLETED 任务批量置「已验证」，重算后各企业评分/等级可能跳档（红绿翻转风险） |
| 前端 | 展示从「N 项整改降 X%」改为「整改率 Y%（已验证权重/总权重）」 |

### 方案 C：折中——计数比值 + 验证门槛（推荐候选）

- 整改率 = 已验证任务数 ÷ 合规任务总数（**等权比值**，不引入权重映射）；
- 保留验证环节（同方案 A）；保留 80% cap 作为可选开关（默认关）；
- 分母为 0 时整改率 = 0（维持 `is_fully_compliant` 兜底分支不变）。

| 维度 | 影响 |
|------|------|
| 与 V4 字面符合度 | ⚠️ 满足「比值 + 已验证」两核心要素；「权重」以等权特化处理（需产品认可「等权即权重=1」的解释） |
| 代码改动 | 中：模型 2 字段 + 迁移 + 引擎改为比值（约 15 行）+ 前端展示微调 + 测试断言改写（约 6 处） |
| 分数行为 | 介于 A/B 之间：降幅与任务完成比例挂钩，直观可解释 |
| 历史数据 | 同方案 B 需批量置「已验证」，但等权口径下跳档幅度小于 B |
| 前端 | 「整改率 = 已验证 X / 共 Y 项」 |

| Q1 | 分母「可整改项」定义 | a) 合规检查发现的全部 findings 数；b) 合规校验生成的全部整改任务（含未完成）；c) 全部整改任务（含 manual） | **b)** —— 与任务体系对齐、可落库统计；a) 会因 findings 未建任务而失真 |

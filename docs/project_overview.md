## 一、项目基础概述

### 1.1 核心定位

「蒙牛全产业链 AI 内生合规决策大脑」是一套**面向中小民企老板的财税合规决策支持系统**，核心思路是**以确定性规则引擎承载专业财税判断**（LLM 负责解释编排、Skill 负责确定精算、Rule Engine 负责法规治理、审计证据链负责留痕存证）。系统模拟金税四期稽查逻辑，从财务数据中识别企业涉税风险，并以「风险扫描 → 合规检查 → 干预解读 → 整改追踪 → 复评报告」的闭环推动企业完成合规整改。

一句话定位：**让税务合规从「知道」到「做到」**——不是告诉企业"你有风险"，而是帮助企业"理解风险并愿意整改"。

### 1.2 研发背景

- **政策环境**：金税四期全面落地，"以数治税"深化，税务、银行、工商等跨部门数据联网，稽查从"抽查"转向"精准识别"。中小企业（占市场主体 90% 以上）财税合规能力最为薄弱，是稽查风险的高发群体。
- **行为根源**：大量涉税风险并非"主观恶意"造成，而是源于老板的**侥幸心态与合规认知不足**——"没被查到就不用管""别人都这么做"。传统税务软件只解决"报税效率"，不解决"决策认知"。
- **赛事背景**：本项目为 **2026 德勤税务精英挑战赛·个人赛道**参赛作品，围绕"税务智能系统优化"主题，结合 AI 大模型与行为经济学，面向真实征纳场景打造完整解决方案。

### 1.3 核心业务痛点

| # | 痛点 | 描述 |
|---|------|------|
| 1 | 风险看不见 | 老板不知道自己的企业处在什么风险状态，缺少可量化的"体检报告" |
| 2 | 侥幸心态重 | "没被查就不算风险"，缺乏对稽查后果（罚款、滞纳金、个税穿透）的具象感知 |
| 3 | 整改无抓手 | 发现问题后不知道改什么、按什么优先级改、改完是否有效 |
| 4 | 征纳沟通低效 | 传统税务通知偏"告知式"，不触动决策者，柔性执法缺乏数字化工具支撑 |
| 5 | 专业门槛高 | 税务法规专业性强，中小企业缺乏专职税务人员，信息严重不对称 |

### 1.4 项目目标与核心价值

**项目目标**：构建"风险扫描 → 合规检查 → 干预解读 → 整改追踪 → 复评报告"的财税合规全闭环，让整改过程"可量化、可追踪、可回溯"。

**核心价值**：

| 视角 | 价值 |
|------|------|
| 企业端 | 提前识别稽查风险、量化损失敞口、获得可执行整改清单，降低合规成本与稽查损失 |
| 税务机关端 | 柔性执法数字化："事前干预"替代"事后处罚"，提升纳税遵从度、缓解征纳矛盾 |
| 专业机构端 | 税务师/代账机构获得批量风险雷达与整改台账，从"记账"升级为"合规顾问" |
| 行业层面 | 行为经济学驱动的遵从度提升路径，可作为税收治理现代化的可复制范式 |

## 二、核心功能模块

### 2.1 功能全景

系统由 **7 大前端页面** 与 **8 个后端纯函数引擎** 组成：

```
蒙牛全产业链 AI 内生合规决策大脑
├── 前端页面（React 18 SPA）
│   ├── Dashboard      数据驾驶舱
│   ├── RiskMap        风险地图（五维全景侦测）
│   ├── Simulator      沉浸式风险模拟器
│   ├── Compliance     合规导航仪
│   ├── Remediation    整改追踪器
│   └── Reports        报告中心
└── 后端引擎（Python 纯函数，全用 decimal 定点运算）
    ├── four_flow_match    四流匹配度计算
    ├── risk_engine        V1 七维度风险评分
    ├── tax_risk_engine    V2 五维全景穿透评估
    ├── penalty_calculator 复合罚款敞口计算
    ├── simulation_engine  三时间节点风险推演
    ├── tax_preference     税收优惠校验
    ├── intervention       分层合规干预策略
    └── compliance_checker 财务数据合规校验
```

### 2.2 模块详情

#### ① 数据驾驶舱（Dashboard）
- **功能**：企业财税概览与关键指标——核心 KPI 卡片、七维度风险雷达图、风险维度柱状图、风险评分趋势折线图；风险卡片按"原始分 → 整改后分"双栏展示。
- **使用场景**：老板/财务打开系统的第一屏，3 秒内掌握企业整体健康度；用于管理层例会与日常巡检。
- **典型输出**：风险总分、七维得分、整改前后对比、行业对标。

#### ② 风险地图（RiskMap）
- **功能**：金税四期视角下的风险可视化——五维全景税务内控侦测（行业基准与宏观内控、增值税 GAAR 穿透、个税隐性分红穿透、行政罚款与滞纳金敞口、综合加权与一票否决），7 个可展开风险卡片，商业/技术双视角切换。
- **使用场景**：风险扫描后查看"问题在哪、多严重、依据什么法规"；整改前后评分演化对比。
- **核心逻辑**：评分统一收敛到单一函数 `compute_compliance_adjusted_risk`，展示"原始分 / 整改后分"两栏，杜绝口径漂移；风险等级为五档（critical / high / medium_high / medium / low），阈值可从 `risk_config` 配置。

#### ③ 沉浸式风险模拟器（Simulator）
- **功能**：输入隐匿收入等场景参数，推演 3 个时间节点的风险演化；指数雪球双路径对比图（合规路径 vs 隐匿路径）、组分分解表（本金+罚金+个税+滞纳金）、同行业案例引用、Trudge 交互式微任务打卡。
- **使用场景**：用"看得见的损失"打破侥幸心态；模拟"如果继续隐匿，3 年后是什么后果"。
- **核心逻辑**：以合规调整后的当前等级为基准（消费统一引擎 `adjusted_level`），叠加场景动态等级，杜绝第二套独立分类规则。

#### ④ 合规导航仪（Compliance）
- **功能**：税收优惠校验（行业基准 + 优惠条件比对）、整改方案对比表、干预策略卡片（按五档风险等级生成差异化解读）。
- **使用场景**：回答"怎么合规"——先查能享受什么优惠，再看需要改什么，最后获得干预建议。

#### ⑤ 整改追踪器（Remediation）
- **功能**：整改任务全生命周期管理（待处理/进行中/已完成）、进度环形图、逾期预警、任务卡片、改善反馈面板（"原始分（整改前）/ 整改后分（调整后）"双栏）、合规复验一键触发。
- **使用场景**：把"整改"从口头承诺变为可追踪的执行闭环；老板与税务顾问在同一看板协作。
- **核心逻辑**：任务完成后自动重评风险分，整改成果直接反映到后续所有页面的"整改后分"。

#### ⑥ 报告中心（Reports）
- **功能**：一键生成综合合规分析报告（HTML 在线查看 + fpdf2 PDF 下载），含风险等级、评分、双状态对比（原始风险 vs 整改后风险、风险降幅、整改状态）、明细发现与建议。
- **使用场景**：面向股东/顾问/税务局的正式交付物；审计留痕。

#### 后端增强能力
- **四流匹配**：合同 ↔ 发票 ↔ 资金 ↔ 申报单据四流比对，精确相等匹配（禁止子串模糊匹配），输出逐侧匹配率与综合评分。
- **罚款敞口计算**：基于《税收征收管理法》第 32/63/68 条，计算行政罚款倍数、日万分之五滞纳金、个税穿透（财税[2003]158号）。
- **合规调整评分**：整改任务完成率与合规发现回流到统一算分函数 `compute_compliance_adjusted_risk`，实现「原始分 / 整改后分」双状态口径，杜绝各接口口径漂移。
- **审计证据链**：每次确定性计算生成 `calc_id`（SHA-256 规范化 JSON 指纹）与参数快照，可回溯「依据哪个规则版本、用了什么数据、谁复核后改了什么」。
- **AI 智能合规顾问**：基于企业数据的对话式问答，配套同行业案例库。

### 2.3 模块逻辑关联

各模块之间形成**完整数据闭环**：

```
数据采集 → 风险扫描 → 合规检查 → 干预解读 → 整改追踪 → 复评报告
   ↑                                                          │
   └────────────────── 整改成果回流（统一算分引擎）──────────────┘
```

- **依赖链**：风险扫描（RiskAssessment）是合规检查、整改任务、报告的公共输入；风险等级与合规调整结果共同驱动干预策略（`intervention.py`）；整改任务完成率回流到统一算分函数，改变所有页面的"整改后分"。
- **统一算分**：全项目所有页面与后端接口的风险评分均收敛到 `compute_compliance_adjusted_risk` / `compute_compliance_adjusted_risks` 两个函数（单条/批量），前端展示"原始分 / 整改后分"双栏，历史快照（原始分）不可变、当前状态（调整后分）随整改演化——这是系统口径一致性的核心保障。

### 3.2 前后端架构设计

**前端（SPA 单页应用）**
- 分层：`pages/`（6 页面）→ `components/`（按业务域拆分 + 通用组件如 TableContainer）→ `store/`（按领域拆分 zustand store，统一 re-export）→ `types/`（前后端契约类型）→ `hooks/`（如 useChartHeight 视口自适应）→ `tests/`（vitest 单元测试）。
- 工程纪律：前后端契约由 `frontend/src/types/` 与后端 Pydantic `schemas/` 双端锁定；窄屏表格统一用 `TableContainer`；大图用 `useChartHeight` 做视口自适应。
- 质量门禁：提交前 `npx tsc --noEmit` 0 错误、`npx vitest run` 全绿（当前 4 文件 / 55 用例）。

**后端（FastAPI 分层）**
- 分层：`api/`（业务域路由，统一在 `__init__.py` 聚合注册）→ `core/`（纯函数引擎：算分、风险、干预、合规、核定扣除、规则治理、PDF）→ `models/`（SQLAlchemy 2.0 ORM）→ `schemas/`（Pydantic 契约）→ `services/`（领域服务）→ `utils/`（PII 脱敏、统一响应）。
- 设计原则：**数值推演严禁大模型参与**，全部由确定性纯函数完成；所有货币/比率字段强制 `decimal.Decimal` + PostgreSQL `NUMERIC`；引擎单元测试覆盖率：compliance_checker 100%、tax_risk_engine 98%。
- 统一响应：`{ code, message, data }` 包装，错误码体系 `200 / 40001（参数校验）/ 40002（业务逻辑）/ 40003（资源不存在）/ 50000（服务器内部错误）`。

### 3.3 部署架构

**开发/演示**（docker-compose，3 服务）
- `frontend`（Nginx + React SPA，公网 80/443）→ `backend`（FastAPI ×2 副本，仅内网 8000）→ `postgres`（PostgreSQL 15，仅内网 5432）；零信任网络，DB 不暴露公网；健康检查驱动启动顺序。
- 生产覆盖 `docker-compose.prod.yml`：每日自动备份（保留 30 天）、DB TLS、backend 副本 3、API 限流、连接池调优。

**生产**（Railway 单容器，当前线上运行）
- 根目录多阶段 `Dockerfile`（前端构建 → FastAPI 运行，前端静态产物由后端同域托管）；Railway 直连 GitHub 仓库自动构建，**push main 即自动重新部署**。
- 启动流程（`start.sh` 自动执行）：等待数据库就绪 → Alembic 迁移 → 幂等 schema 同步（`migrate_schema.py`）→ 幂等种子导入 → 启动 uvicorn（监听注入 PORT）。
- 线上地址：`https://tax-mind-production.up.railway.app`（前后端同域，默认账号 `admin_t1` / `a123456`）。

### 3.4 核心技术选型原因

| 选型 | 原因 |
|------|------|
| Python + FastAPI | 与"纯函数引擎 + 强类型校验 + 高并发异步"高度契合；Pydantic v2 保障接口契约 |
| SQLAlchemy 2.0（async）+ asyncpg | 原生异步性能 + 类型化 ORM；PostgreSQL 15 的 NUMERIC 保证金额精度 |
| decimal.Decimal 定点运算 | 税务金额/比率绝不允许浮点误差；CI 覆盖率对核心引擎 ≥70% 门槛 |
| React 18 + Vite 5 + TS | 生态成熟、构建快；TS 全链路类型安全支撑多租户复杂前端 |
| AntD + Tailwind + Recharts | 企业级组件、原子化样式、可视化图表，7 页面快速成型 |
| 多租户隔离 + JWT + AES-256-GCM | 面向审计机构多客户场景；字段级加密保护敏感数据（满足等保 2.0 三级） |
| fpdf2 中文字体自动检测 | 跨平台生成 PDF 报告，避免硬编码字体路径导致部署后乱码 |
| GitHub Actions + Railway | 扫描/测试/构建/部署全自动，push 即上线，演示与交付零运维负担 |

### 3.5 数据流转逻辑

```
用户操作（选择企业/上传数据）
   → React SPA（页面组件 → zustand store → api client）
   → FastAPI 网关（JWT 鉴权 + 租户 403 校验 + 统一响应）
   → 核心引擎（风险扫描/合规干预/模拟等纯函数，decimal 运算）
   → PostgreSQL（企业档案、流水、发票、合同、申报、评估、任务、报告）
   → 结果回流前端（雷达图/卡片/双栏评分/PDF 报告）
```

**数据安全链路**：传输层 TLS 加密 → 应用层 JWT + 租户级 403（企业不存在或租户不一致统一抛 403，不泄露存在性）→ 存储层 PII 星号脱敏 + AES-256 字段加密 → 对外 API 统一 `sanitize_response` 脱敏。核心引擎的数据流（风险扫描、模拟、合规校验）详见 `docs/architecture.md` 时序图。

### 4.2 当前迭代阶段与已完成核心功能

**当前阶段**：V0.3——统一算分收口与合规干预深化。已完成的关键工程：

- 全项目算分逻辑统一收敛到 `compute_compliance_adjusted_risk`（单条/批量），前端"原始分 / 整改后分"双栏展示（风险地图、数据驾驶舱、整改追踪、报告中心）；

- 多租户 403 级数据隔离（13 个端点接入 + 18 用例防回归测试）；

- 前端 55 用例、后端核心引擎覆盖率 98%~100% 的测试基线。

### 5.4 生产部署操作手册（Railway 单容器）

1. **创建数据库**：Railway 项目内添加 PostgreSQL 插件（或任意外部 Postgres）。
2. **关联仓库**：连接 GitHub 仓库 `tax-mind`，Railway 自动检测根目录 `Dockerfile` 并构建（Railway 无法解析 docker-compose，必须用 Dockerfile 部署）。
3. **配置环境变量**（服务 Variables）：

   | 变量 | 说明 |
   |------|------|
   | `DATABASE_URL` | Postgres 插件提供，`postgresql://...`（后端自动转为 `+asyncpg`） |
   | `JWT_SECRET_KEY` | 随机 32+ 位字符串，缺失则拒绝启动 |
   | `ENCRYPTION_KEY` | Base64 编码 32 字节密钥（AES-256-GCM），缺失则拒绝启动 |
   | `DEBUG` | 生产环境建议 `false` |
   | `LLM_PROVIDER` / `DEEPSEEK_API_KEY` / `QWEN_API_KEY` | 可选，用于 AI 合规助手，未配置自动降级 Mock |

4. **启动流程**（`start.sh` 自动）：等待 DB 就绪 → `alembic upgrade head` → 幂等 schema 同步 → 幂等种子导入 → 启动 uvicorn。
5. **上线验证**：
   ```bash
   curl https://<你的域名>/api/v1/health
   # → {"code":200,"data":{"status":"ok","version":"0.3.0"}}
   ```
6. **更新发布**：本地 `git push origin main` → CI 校验 → Railway 自动重新部署。

### 5.5 常见问题排查

| 现象 | 原因与处理 |
|------|-----------|
| 前端"接口全挂、重试无效"，控制台 HTTP 500 | 多为后端端口不一致：对比 vite 代理 target（默认 `http://localhost:8000`）与后端实际监听端口（`Get-NetTCPConnection -State Listen`） |
| API 返回 `relation "enterprises" does not exist` | 首次启动迁移未执行：重启 backend 自动执行，或手动 `python -c "import asyncio; from app.database import init_db; asyncio.run(init_db())"` |
| 生产全接口 500，日志 `column ... does not exist` | schema 漂移：确认运行了 `migrate_schema.py`（start.sh 生产分支自动执行），或手动 `python scripts/migrate_schema.py` |
| 登录失败 / 401 | 检查 `JWT_SECRET_KEY`；确认执行过 `seed_multi_tenant.py` |
| 部署后旧页面报 chunk 404 | 浏览器缓存了旧 index.html：硬刷新（Ctrl+Shift+R）；已加 `Cache-Control: no-cache` 防复发 |
| LLM 功能报错 | 检查 `DEEPSEEK_API_KEY`/`QWEN_API_KEY`；未配置时系统降级 Mock，不影响风险扫描/合规干预/模拟 |
| PDF 报告中文乱码 | 确认安装 `fpdf2`；字体加载走跨平台检测函数，勿硬编码路径 |
| Windows 下 pytest 偶发文件锁（WinError 32） | 测试临时 SQLite 句柄释放延迟，`tests/test_api/conftest.py` 已加重试缓解 |

## 六、维护与贡献规范

### 6.1 维护主体

- **当前维护**：项目以赛事参赛个人/团队为主体维护（多租户种子含"安永审计一组/二组"组织模型，定位为审计/涉税服务机构场景）。
- **仓库**：GitHub 私有仓库 `tax-mind`，`main` 为主干，Railway 直连自动部署。
- **文档体系**：`docs/` 下含架构、部署、接口、测试、AI 协作日志、综合审计报告、隐私政策、数据处理协议、服务条款、等保合规说明等全套文档，作为维护与交接依据。

### 6.2 版本迭代规则

- **版本号**：后端 `app/config.py` 维护 `app_version`（当前 `0.3.0`），格式 `主.次.修订`；重大架构调整升主版本，功能增量升次版本，修复升修订。
- **迭代节奏**：以"说明书/需求 → 研判 → 实现 → 门禁验证 → 提交"为单次迭代闭环；同一版本内可多次提交。
- **变更留痕**：关键架构决策写入 `docs/ai_collaboration_log.md` 与项目记忆；版本发布跟随 git 提交自动部署。

### 6.3 代码提交规范

- **提交前门禁（硬性）**：
  ```bash
  cd frontend && npx tsc --noEmit        # 0 错误
  cd frontend && npx vitest run           # 全绿（当前 55 用例）
  cd backend && python -m pytest          # 无新增失败；核心引擎覆盖率 ≥70%（CI）
  ```
- **提交信息**：使用中文、简要描述"改了什么 + 为什么"（如"报告中心改显式双状态并消除模拟器独立降级规则，统一算分口径"）；一次提交只包含相关改动，禁止混入无关文件。
- **敏感文件红线**：`.env`、密钥、凭据、本地数据库一律不入库；新增环境变量只提交 `.env.example` 模板。
- **噪声文件管理**：CRLF/BOM 等行尾噪声改动（如部分历史文件）不纳入无关提交。

### 6.4 外部贡献者参与流程（建议）

> 当前项目为单维护者直推 `main` 模式；已配置 GitHub Actions 的 PR 触发工作流，以下为对外协作的推荐流程。

1. **了解**：先阅读 `README.md` 与本文档，理解统一算分、目录分层、租户隔离等既有约定，避免破坏架构纪律。
2. **Fork / 分支**：Fork 仓库或创建特性分支 `feat/<描述>`。
3. **实现**：遵循既有分层与命名（后端 `api/core/models/schemas`，前端 `pages/components/store/types`）；所有算分逻辑必须复用统一函数，禁止另起炉灶。
4. **验证**：通过 §6.3 全部门禁；新增/修改功能配套单元测试。
5. **发起 PR**：提交 PR 到 `main`，描述变更动机与验证结果；CI（Ruff、Bandit、pytest、tsc、ESLint）须全绿。
6. **评审与合并**：经维护者评审通过后合并；合并即自动触发生产部署。
